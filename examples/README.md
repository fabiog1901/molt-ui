# PostgreSQL → CockroachDB migration example

This example walks through an order-management database migration: create and seed
PostgreSQL, adapt a few data types, load the data into CockroachDB with MOLT, and
restore indexes, constraints, and audit triggers.

## Files

| File | Purpose |
| --- | --- |
| [pg.order_demo.sql](pg.order_demo.sql) | Recreate the PostgreSQL database and its objects. |
| [pg.seed.yaml](pg.seed.yaml) | Define the sample data generated by `dbworkload`. |
| [pg.import-data.sql](pg.import-data.sql) | Import the generated files into PostgreSQL and report row counts. |
| [crdb.pre-migration.sql](crdb.pre-migration.sql) | Recreate the CockroachDB database with the schema needed for loading. |
| [transformation.json](transformation.json) | Exclude source columns that are replaced or computed on the target. |
| [crdb.post-migration.sql](crdb.post-migration.sql) | Restore unique constraints, secondary indexes, foreign keys, and audit triggers. |

## Before you start

You will need PostgreSQL, CockroachDB, `psql`, `dbworkload`, and a MOLT binary.
The example migration uses an S3-compatible bucket accessible to both MOLT and
CockroachDB; configure its credentials and endpoint before running the migration.

Run the commands below from this directory. From the repository root:

```bash
cd examples
```

**Both schema setup scripts drop and recreate the `order_demo` database on their
respective servers.** Use databases intended for this example.

## 1. Create and seed PostgreSQL

Create the source database and schema. The script connects to `postgres` before
recreating `order_demo`:

```bash
psql -X -v ON_ERROR_STOP=1 -d postgres -f pg.order_demo.sql
```

Generate the sample data:

```bash
dbworkload util csv \
  --input pg.seed.yaml \
  --output data \
  --procs 4 \
  --csv-max-rows 100000
```

This writes tab-separated `.tsv` files into `data/`. Keep the process count and
chunk size shown above: the import script references those generated filenames.

Load the files into the empty source tables:

```bash
psql -X -v ON_ERROR_STOP=1 -d order_demo -f pg.import-data.sql
```

The script finishes by reporting the expected row counts:

| Table | Rows |
| --- | ---: |
| `audit.audit_event` | 0 |
| `order_demo.addresses` | 10,000 |
| `order_demo.categories` | 12 |
| `order_demo.customers` | 10,000 |
| `order_demo.order_items` | 3,000,000 |
| `order_demo.orders` | 1,000,000 |
| `order_demo.payments` | 1,000,000 |
| `order_demo.products` | 250 |
| `order_demo.shipments` | 1,000,000 |

## 2. Prepare source columns for migration

The source schema includes three types that this example replaces with scalar
columns on CockroachDB:

| Source column | PostgreSQL type | Replacement columns |
| --- | --- | --- |
| `addresses.coordinates` | `point` | `coordinates_x`, `coordinates_y` (`FLOAT8`) |
| `products.available_during` | `daterange` | `available_from`, `available_to` (`DATE`) |
| `shipments.delivery_window` | `tstzrange` | `delivery_from`, `delivery_to` (`TIMESTAMPTZ`) |

Connect to the PostgreSQL `order_demo` database and run the following once. These
generated columns expose the values that MOLT will copy into ordinary target
columns:

```sql
ALTER TABLE order_demo.addresses
  ADD COLUMN coordinates_x DOUBLE PRECISION GENERATED ALWAYS AS (coordinates[0]) STORED,
  ADD COLUMN coordinates_y DOUBLE PRECISION GENERATED ALWAYS AS (coordinates[1]) STORED;

ALTER TABLE order_demo.products
  ADD COLUMN available_from DATE GENERATED ALWAYS AS (lower(available_during)) STORED,
  ADD COLUMN available_to DATE GENERATED ALWAYS AS (upper(available_during)) STORED;

ALTER TABLE order_demo.shipments
  ADD COLUMN delivery_from TIMESTAMPTZ GENERATED ALWAYS AS (lower(delivery_window)) STORED,
  ADD COLUMN delivery_to TIMESTAMPTZ GENERATED ALWAYS AS (upper(delivery_window)) STORED;
```

The range replacements store the endpoints; they do not preserve all PostgreSQL
range semantics, such as bound inclusivity or the distinction between empty and
unbounded ranges.

## 3. Prepare CockroachDB

Review [crdb.pre-migration.sql](crdb.pre-migration.sql) and apply it to the target
server. Connect to an existing database such as `defaultdb`; the script creates
and switches to `order_demo`.

The initial schema omits secondary indexes, unique constraints, foreign keys,
and audit functions and triggers. At the end of the script, the original point
and range columns are replaced with the scalar columns listed above.

The [transformation file](transformation.json) tells MOLT to exclude:

- The original `coordinates`, `available_during`, and `delivery_window` columns.
- The source computed columns `products.search_document`, `order_items.line_total`,
  and `orders.total`, which CockroachDB computes itself.

The replacement coordinate and endpoint columns are migrated as ordinary values.
The exclusions prevent MOLT from expecting the original columns on the target or
trying to load values into its computed columns.

## 4. Run the migration

Set your source and target connection URLs, replacing the example credentials:

```bash
export SOURCE_URL='postgres://USER:PASSWORD@localhost:5432/order_demo'
export TARGET_URL='postgres://USER:PASSWORD@localhost:26257/order_demo?sslmode=require'
```

Run MOLT from this directory. This command uses the patched binary built for
this example; adjust the executable path if needed:

```bash
../molt/molt-point-rustfs fetch \
  --source="$SOURCE_URL" \
  --target="$TARGET_URL" \
  --bucket-path='s3://order-demo/' \
  --flatten-partitioned-tables \
  --table-handling=none \
  --transformations-file=transformation.json
```

`--table-handling=none` preserves the target schema prepared in the previous
step. `--flatten-partitioned-tables` loads the partitioned PostgreSQL orders table
into its unpartitioned CockroachDB counterpart.

## 5. Restore target indexes, constraints, and triggers

After the data load succeeds, apply
[crdb.post-migration.sql](crdb.post-migration.sql) to the CockroachDB `order_demo`
database:

```bash
psql -X -v ON_ERROR_STOP=1 "$TARGET_URL" -f crdb.post-migration.sql
```

This script restores the unique constraints and secondary indexes, validates
foreign keys against the migrated rows, and installs the audit function and its
update triggers. Apply it once; its statements run separately, so changes made
before an error remain in place.
